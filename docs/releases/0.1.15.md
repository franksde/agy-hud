# 0.1.15 验证记录

日期：2026-11-05。起点：`568a8ec`（0.1.14 之后）。触发来源：issue #18（@Dear47，Antigravity CLI 1.5.0 上状态栏在 working → idle 后约 10 秒被 `signal: killed`）。

合入方式：分支 `feature/issue-18` 的 5 个 commit 线性 fast-forward 到 `main`。第一个 commit 由 codex 执行（`gpt-6.1-sol`、`high`），其余由维护者按 TDD 完成，审查修复同样先补失败测试。

## 成因核实

issue 给出的成因是「HTTPS、HTTP 两次都返回 401，各等 5 秒」。核对代码与实测后，这一点不成立，但被杀本身属实：

- 401 很快：HTTPS 收到 401 时，`queryLanguageServer` 直接返回 `probeAuthRejected`，不会再试 HTTP。在本机 CLI 1.5.1 上用 `agy -p /usage` 拉起真实进程实测，4 个 loopback 端口都在 0.1 秒内回 401，或在纯 HTTP 端口上 TLS 握手失败，没有挂起的。
- 真正会卡 10 秒的是「接受连接、但一直不应答」的端口：HTTPS 5 秒，再 HTTP 5 秒，每个端口都这样，整次探测又没有总时限。伪造一个名为 `agy`、带两个此类端口的进程，0.1.14 的 working → idle 帧跑了 30.3 秒。
- 另一条同样会被杀的路径：CLI 有时写完 payload 不关 stdin（antigravity-cli#698），`readStdin` 只等 `end`、没有时限。日志里的 `failure 1/30` 就是 CLI 连续失败 30 次后自动停用状态栏的计数。
- 被杀的那次没来得及保存刷新状态，状态文件里仍是 working，于是下一个 idle 帧又走同步刷新，又被杀。

CLI 的 kill 超时没能从二进制里确认，#698 里的实测是 5–10 秒。1.5.0 本机没有，所以 reporter 那台机器上到底是哪条路径，没能复现确认，两条都修了。

## 行为

- **同帧刷新有了总时限**：working → idle 那一帧最多等 2000 ms（`sameFrameRefreshBudgetMs`）。超时后用已有缓存渲染，`AbortSignal` 一路传到 http/https 请求并销毁 socket，`refreshQuota` 不再遍历后面的端口和候选进程，也不写缓存、marker 或 hint。之后照常执行 `triggerBackgroundRefreshIfNeeded`：保存 idle 状态，并按需派后台刷新，下一帧不会再走同步刷新。
- **单个请求有墙钟时限**：每个 loopback 请求发出后 1500 ms 未完成就放弃（`loopbackRequestTimeoutMs`）。原来用的是 `req.setTimeout`，那是 socket 闲置超时：实测 1500 ms 设置下，一个卡住的 TLS 握手要约 3 秒，一直滴数据的回复则永远不会超时。响应体中途断开时立即结束，不等计时器。后台的 `quota refresh` 同样受这个时限约束，它本身没有总时限，这是有意的。
- **`ps` / `lsof` 有时限**：两者都是同步执行，2 秒的等待打断不了它们，所以各自限时 1000 ms（`discoveryCommandTimeoutMs`，`processIdentity` 复用同一常量）。`ps` 超时现在返回失败结果，不再抛异常。
- **不再等 stdin 关闭**：输入一旦能解析为完整的 JSON 对象就开始渲染；1000 ms 内收不到完整对象就放弃（`stdinTimeoutMs`），空输入照旧输出 `agy-hud`。读完后移除监听、pause 并 destroy stdin，避免打开的管道拖住进程。直接接 bundle 时，嵌套 `/usage` 路径同样适用；经 `hooks/status-line.sh` / `.cmd` 时，嵌套路径仍由 hook 读到输入结束（见「未做」）。
- **文档**：两份 README 的 CLI 一节写明上述时限及其约束范围，Limitations 写明 hook 嵌套路径的行为；CHANGELOG 同步。

## 独立审查轨迹

每轮两路并行，同一份提示词，提示词里写了基线句：codex（`gpt-6.1-sol`、`high`，Codex CLI read-only）和 agy（`gemini-3.8-flash-high`，`--mode plan`）。阵容按 Frank 指定。第一个 commit 是 codex 写的，所以 r1 的 codex 那一路是在审自己写的代码；r2 起审的是维护者的提交。

- r1（范围：第一个 commit）：
  - codex P2：1500 ms 只有常量测试，把实现改回 5000 ms 测试仍全绿。已修：超时可注入，新测试真跑超时路径。
  - codex P3：`req.setTimeout` 是 socket 闲置超时，文档里「1.5 秒」写过了（实测 HTTPS 约 3 秒）。已修：改为墙钟计时器。
  - 两路 P3：同步 `ps` / `lsof` 没有时限，2 秒预算拦不住（pre-existing）。#18 的根因未坐实，成本低，一并修了。
  - 两路：计时断言 250 / 400 ms 在慢机器上可能误报。已放宽到 1000 ms。
- r2（范围：stdin 修复与 r1 修复两个 commit）：
  - codex P2：响应体中途断开时，新加的计时器不会被清，进程会多挂到计时器触发。已修。
  - codex P2：墙钟测试分不出「退回闲置超时」这种回归。已补「持续滴数据」测试，变异验证：换回 `req.setTimeout` 后变红。
  - codex P2：测试里造假可执行文件的逻辑和 `fakeAgy` 重复。已提取 `test/fakeExecutable.ts`，三处复用。
  - agy P2：`ps` 超时会让 `refreshQuota` reject。已改为返回失败结果。
  - 两路：hook 的嵌套 `/usage` 路径仍等到 EOF，CHANGELOG 写过了。判为 pre-existing，不改 hook（sh 只读一行也挡不住没有换行的 payload，cmd 本机无法测），收窄 CHANGELOG 措辞，写入 Limitations。
  - codex P3：held-open 测试在 `exit` 时读 stdout，可能没收全。已改为等 `close`。agy P3：放弃的 stdin 上补空 error 监听。已修。
  - 不改：多个候选的 `lsof` 超时会累加超过 2 秒（pre-existing 循环，README 已写明各自 1 秒、不受 2 秒约束）。
- r3（范围：r2 修复 commit）：agy 无发现。codex 一条 P2：滴数据测试在回归时会挂住测试进程（`finally` 不执行）。已修：加会 reject 的 watchdog，变异验证回归时约 1 秒自行退出。没有 P1，按上限不开第 4 轮，收敛。
- 每轮跑完都核对过：两路审查的 worktree 没有被改动，主 worktree 仍在 `main`。
